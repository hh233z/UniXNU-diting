# CPU 与软件显示诊断

第54版实机记录：8核在最后一秒采样均在线，负载1%至3%。快照在30/90/180秒附近覆写同一文件，故不能把最后一秒当成整个操作过程的负载。35秒BackBoard栈捕获到QuartzCore软件颜色矩阵、扫描行和高斯模糊，尚无耗时占比。

后续诊断只在 diting_boot_snapshot=1 且 ST 输入实际初始化成功后启动。等待30秒后连续记录36个五秒窗口，保存于 Data 的 /logs/DitingCpu-timeline.txt，总观察时间约180秒。每次启动首次写入截断旧记录，最多36条，不生成测试负载。各核 busy_pct 来自真实调度空闲时间差；sample_valid=0 表示窗口无法可靠计算，不能当零负载。frequency_measured=0 表示没有实测工作频率。

每条记录还保存累计帧提交、完成、绘制、表面完成等待、刷新节拍等待计数。时间单位为 mach ticks，分析时用同一窗口的 elapsed_mach 或实际19.2MHz时基换算。计数逐项原子读取，跨字段不是同一个事务快照，适合数秒区间差值。统计覆盖内核帧缓冲阶段，不含用户态CoreAnimation合成本身；不能把内核绘制耗时当完整帧耗时。失败帧可能增加提交与等待而不增加完成，二者差值还可能包含在途请求，不能直接全算丢帧。

不更改频率、电压、热限、渲染协议或真实表面完成条件。CPU表面没有GPU writer时不会因500ms超时常量自动等待500ms。下一轮先判断活跃窗口的CPU分布、帧到达速度和内核阶段耗时，再决定修改合成、同步或调频。

## 第55版结果与EPSS补充

36个连续窗口证明8核实际参与，活动时多数核心可达65%至89%，X2最高95%；低负载出现在无新帧窗口。3167帧内核绘制平均1.58ms，表面等待约0.00056ms/帧，慢片段提交约8至11FPS。BackBoard栈指向软件纹理采样/扫描行/高斯模糊及dispatch_apply，需优先定位上游合成。

后续版本对照MiCode/Xiaomi_Kernel_OpenSource bsp-diting-s-oss的drivers/cpufreq/qcom-cpufreq-hw.c，将LUT核心数字段修正为bits18:16。Android实读DT确认三域0x17d91000/92000/93000、PDMEM0x17d09804/808/80c，未设置no-accumulative-counter。新增snapshot开启时的EPSS请求/状态只读遥测及每约500ms逐核32位周期计数差，间隔超过1秒作无效以避免多次回绕歧义。effective_cycle_khz是周期/墙钟时间，可能包含空闲的影响，不等于瞬时工作频率。DOMAIN_STATE与热限IRQ也不单独证明当前频率。frequency_measured=0仍表示没有瞬时频率测量。没有改变电压、热限、档位上限或调频策略；无法保证该字段修正会改善本机性能。
